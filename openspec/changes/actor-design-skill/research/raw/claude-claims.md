# All claims extracted by the Claude research run (115; only 25 went through 3-vote verification)


## Source:   (fields: ['claim', 'quote', 'importance'])

- **C1** [central] Orleans' official guidance names a single coordinator, registry or monitor grain as a bottleneck to avoid, and gives staged (multi-level) aggregation as the fix when aggregation is needed. This is one framework's design opinion, but it matches the general singleton-bottleneck anti-pattern.
  - quote: Avoid bottleneck grains. Single coordinator/Registry/Monitor. Do staged aggregation if required.
- **C2** [central] On granularity, Orleans advises choosing grain size from the application domain model (for example one grain per user or order), prefers many small grains over a few large ones for throughput, and says that grains which talk to each other a lot are a sign they should be merged into one grain.
  - quote: Optimal throughput is achieved by using multiple smaller grains rather than a few larger grains. However, the best practice of choosing a grain size and type is based on the application domain model. [...] Highly chatty grains may be better combined as a single grain.
- **C3** [central] If actors handle one request at a time (Orleans grains are non-reentrant by default), then a cycle of request-reply calls between actors (self-call, A->B->A, A->B->C->A) can deadlock; Orleans only breaks such deadlocks by timeout, and the alternative of allowing reentrancy is described as error-prone because calls interleave.
  - quote: Grains are non-reentrant by default. Deadlock can occur due to call cycles.
- **C4** [central] Orleans states that the virtual actor model is a poor fit when entities must share memory, when there are a small number of large entities, when global coordination or global consistency is needed, or for long-running batch-style operations; it fits a large number of loosely coupled, mostly independent entities with interactive (request-response) workloads and no single point of synchronization.
  - quote: Global coordination and/or consistency are needed. Such global coordination would severely limit the performance of an Orleans-based application.
- **C5** [supporting] Orleans delivers each message at most once and puts retry responsibility on the caller, with the stated common practice being an end-to-end retry from the client or front end rather than per-hop retries. This is a framework-specific assumption that changes the design: a retried call can run twice, so handlers reached by retries need to be safe to repeat (the idempotency consequence is inference, not stated on the page).
  - quote: Orleans provides a message delivery guarantee where each message is delivered at-most-once. It is the responsibility of the caller to retry any failed calls if needed. Common practice is to retry from end-to-end from the client/front end.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C6** [central] P expresses a system as a collection of interacting state machines that communicate only by events, and the same program serves as both the executable implementation and the model that is checked: it compiles to code and is also tested by model checking. This is primary evidence for the design idiom 'each actor is an explicit state machine' and for design-level verification of an actor protocol (well established for P; it is one tool's approach, not a general actor-framework rule).
  - quote: P allows the programmer to specify the system as a collection of interacting state machines, which communicate with each other using events. P unifies modeling and programming into one activity for the programmer. Not only can a P program be compiled into executable code, but it can also be tested using model checking techniques.
- **C7** [central] P's default correctness property is 'responsiveness': every machine must handle every event that can arrive in every state, and the default safety checker reports any unhandled event. As a review criterion this means a state-by-message table with no empty cell (each cell is handle, defer or an explicit ignore).
  - quote: The P language is designed so that a P program can be checked for responsiveness—the ability to handle every event in a timely manner. By default, a machine needs to handle every event that arrives in every state. [...] The default safety checker looks for presence of unhandled events.
- **C8** [central] Because handling every event in every state is impractical, P makes postponing an event an explicit, per-state annotation (deferred events), and adds a default liveness check that no event can be deferred forever. Design implication: postponing a message (stash/defer) must be a declared decision per state, and the design must show the message is eventually handled.
  - quote: But handling every event in every state is impractical. The language provides a notion of deferred events where the programmer can annotate when she wants to delay processing an event. [...] The language also provides default liveness checks that an event cannot be potentially deferred forever.
- **C9** [supporting] In P the outside world (the environment) is modelled explicitly as nondeterministic 'ghost machines' that close the system for testing; they are erased when compiling to executable code, and a type system guarantees the erasure does not change the program's behaviour. Design implication: to verify an actor design, model each external party as a nondeterministic actor that can send any message its protocol allows.
  - quote: P allows the programmer to specify the environment, used to “close” the system during testing, as nondeterministic ghost machines. Ghost machines are erased during compilation to executable code; a type system ensures that the erasure is semantics preserving.
- **C10** [supporting] P was used in production to implement and verify the core of the USB device driver stack shipped in Microsoft Windows 8, and the authors report the result is more reliable and faster than the earlier non-P driver (an experience report by the tool's own authors; the abstract gives no figures).
  - quote: P was used to implement and verify the core of the USB device driver stack that ships with Microsoft Windows 8. The resulting driver is more reliable and performs better than its prior incarnation (which did not use P); we have more confidence in the robustness of its design due to the language abstractions and verification provided by P.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C11** [central] Dapr's official guidance says the actor pattern fits a problem made of a large number (thousands or more) of small, independent, isolated units of state and logic. This is a granularity rule: many small actors, each owning its own state, not a few large ones. (One framework's stated opinion; consistent with Orleans guidance.)
  - quote: Your problem space involves a large number (thousands or more) of small, independent, and isolated units of state and logic.
- **C12** [central] Dapr says actors are a poor fit when external components need significant interaction with them, and it names querying state across a set of actors as the example. Design consequence: cross-actor queries should not be answered by asking many actors; they need a read model or another store. (One framework's opinion; the read-model consequence is inference.)
  - quote: You want to work with single-threaded objects that do not require significant interaction from external components, including querying state across a set of actors.
- **C13** [central] Dapr lists as a condition for using actors that an actor must not block its callers with unpredictable delays from I/O. The page ties this to its turn-based access model (one call at a time per actor), so a slow external call inside an actor holds up every caller behind it. (One framework's opinion; the link to turn-based access is on the same page: "The Dapr actor runtime provides a simple turn-based access model for accessing actor methods.")
  - quote: Your actor instances won’t block callers with unpredictable delays by issuing I/O operations.
- **C14** [supporting] Dapr separates the two jobs: actors encapsulate state and behaviour with an identity, while multi-step business processes that span several services belong in a workflow (a higher-level abstraction built on actors), not in hand-written coordinating actors. This differs from Akka/Erlang advice, where a process manager or saga is itself an actor. (One framework's opinion.)
  - quote: You would use Dapr Workflow when you need to define and orchestrate complex workflows that involve multiple services and components.
- **C15** [supporting] Dapr offers two ways for an actor to schedule work on itself, and the design choice is durability: a timer is lost when the actor is deactivated, a reminder is persisted in the actor state store and survives. So a deadline or timeout that must fire after deactivation or a crash has to be a reminder, not a timer. (Documented framework behaviour; the 'must be a reminder' rule is inference from it.)
  - quote: The main difference is that Dapr actor runtime is not retaining any information about timers after deactivation, while persisting the information about reminders using Dapr actor state provider.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C16** [central] Pekko's worked IoT example designs an actor protocol-first: the messages are the actor's API (the counterpart of an object's interface), and design of the device actor starts by identifying the messages it will receive, sorted into known message patterns such as request-respond. This is one framework's stated method (inherited from the Akka guide), consistent with wider actor practice.
  - quote: If we were working with objects, we would typically design the API as interfaces, a collection of abstract methods to be filled out by the actual implementation. In the world of actors, protocols take the place of interfaces. While it is not possible to formalize general protocols in the programming language, we can compose their most basic element, messages. So, we will start by identifying the messages we will want to send to device actors.
- **C17** [central] Request-reply is modelled as two separate messages (a request that carries the reply address, and a reply), and the guide says a version without a correlation id is 'correct' only for local use: once the requester may resend after a timeout or query several actors, the request must carry a requester-supplied ID and the responder must echo that same ID in the reply.
  - quote: Our first query protocol was correct, but did not take into account distributed application execution. If we want to implement resends in the actor that queries a device actor (because of timed out requests), or if we want to query multiple actors, we need to be able to correlate requests and responses. Hence, we add one more field to our messages, so that an ID can be provided by the requester
- **C18** [central] The guide tells designers to assume any message can be lost, for local as well as remote sends, because an actor crashing while processing a message loses that request just as a remote host crash does. The stated condition is Pekko's at-most-once delivery ('no guaranteed delivery'); the design rule is to write every actor so that loss of any single message is tolerated.
  - quote: Even though in both cases, the service recovers after a while (the actor is restarted by its supervisor, the host is restarted by an operator or by a monitoring system) individual requests are lost during the crash. Therefore, writing your actors such that every message could possibly be lost is the safe, pessimistic bet.
- **C19** [central] A transport-level delivery guarantee does not give a domain-level guarantee: only the application can say that work succeeded, so success must be reported by an explicit application-level acknowledgement message sent after the work is actually done (for the device: a TemperatureRecorded reply, with an ID, sent after the state update; for an order: only after the database confirmed the write). A fire-and-forget write command is called out as insufficient because the sender 'can never be sure if the message was processed or not'.
  - quote: This illustrates that the guarantee of delivery does not translate to the domain level guarantee. We only want to report success once the order has been actually fully processed and persisted. The only entity that can report success is the application itself, since only it has any understanding of the domain guarantees required. No generalized framework can figure out the specifics of a particular domain and what is considered a success in that domain.
- **C20** [supporting] Message order may be relied on only per sender-receiver pair and only for direct sends: messages from different senders can interleave at the receiver, any message may still be dropped, and the ordering guarantee is lost when messages pass through a mediator. A design that depends on order across senders or through intermediaries is therefore relying on something the runtime does not promise (Pekko-specific guarantee, stated as a condition).
  - quote: In Pekko, for a given pair of actors, messages sent directly from the first to the second will not be received out-of-order. The word directly emphasizes that this guarantee only applies when sending with the tell operator directly to the final destination, but not when employing mediators.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C21** [central] Cloudflare's guidance says the first and most important design decision is what each Durable Object (actor) stands for, and the answer is one object per logical unit that needs coordination (a chat room, game session, document, a user's data, a tenant's workspace), each with its own single-threaded execution and private storage in place of a shared database with locks. This is one framework's opinion, but it matches the 'one actor per consistency boundary' idiom.
  - quote: The most important design decision is choosing what each Durable Object represents. Create one Durable Object per logical unit that needs coordination: a chat room, a game session, a document, a user's data, or a tenant's workspace. This is the key insight that makes Durable Objects powerful. Instead of a shared database with locks, each "atom" of your application gets its own single-threaded execution environment with private storage.
- **C22** [central] A single global actor that all traffic passes through (for example a global rate limiter or global counter addressed by one fixed ID) is named an anti-pattern because it becomes a throughput bottleneck. The stated fix is to find natural coordination boundaries (per user, per room, per document) and create one object for each. The page gives a rough capacity of 500-1,000 requests per second per object for simple operations as the number to size the 'atom' against.
  - quote: A single Durable Object handling all traffic becomes a bottleneck. While async operations allow request interleaving, all synchronous JavaScript execution is single-threaded, and storage operations provide serialization guarantees that limit throughput. A common mistake is using a Durable Object for global rate limiting or global counters. This funnels all traffic through a single instance
- **C23** [central] For hierarchical data the guidance is a parent-child split, not one object holding everything: the parent coordinates and keeps an index of its children, and each child owns its own state. The claimed benefits are that work on different children runs in parallel while each child stays single-threaded, and that listing children only asks the parent (the children are not woken).
  - quote: Do not put all your data in a single Durable Object. When you have hierarchical data (workspaces containing projects, game servers managing matches), create separate child Durable Objects for each entity. The parent coordinates and tracks children, while children handle their own state independently.
- **C24** [central] In Durable Objects an actor does NOT strictly handle one request to completion before the next: while a handler waits on non-storage I/O such as an outbound fetch() call, other requests can interleave and change state, so a check-then-call-external-then-write sequence can race. The stated design fix is optimistic locking (read a version before the external call, verify it is unchanged before writing). This is a runtime property that changes a design decision, and it differs from frameworks where an actor handles one message at a time by default.
  - quote: Input gates only protect during storage operations. Non-storage I/O like `fetch()` or writing to R2 allows other requests to interleave, which can cause race conditions
- **C25** [supporting] Each actor should own its own timers (alarms) for per-entity scheduled work, scheduled only when there is work to do, and because an alarm can fire more than once the alarm handler must be idempotent (the page's example checks a stored 'last renewal' time before repeating the side effect).
  - quote: In rare cases, alarms may fire more than once. Your `alarm()` handler should be safe to run multiple times without causing issues.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C26** [central] An empirical study of 186 real-world Akka actor bugs (130 from Stack Overflow, the rest from GitHub) classifies root causes into ten categories: Logic (19.4%, most common), Race (14.6%), API Confusion (14.0%), Explicit Life Cycle (12.4%), Programming (12.4%), Messaging Patterns (9.7%), Model Confusion (7.6%), Misnaming, Misconfiguration and Untyped Communication (1.1%, least common). Evidence is from one framework (Akka) only, so it is well-established for Akka and inference for other actor systems.
  - quote: root causes of our actor bugs can be classified into ten categories, with Logic as the most common root cause and Untyped Communication as the least common
- **C27** [central] Race is the second most common root cause (14.6%), and 29.6% of those Race bugs come from one anti-pattern: closing over the actor's mutable sender() inside a future callback, scheduled message or task, so the reply goes to the wrong actor or to dead letters. The fix is to capture the reply address in a local value before the asynchronous step. The paper presents this as a misuse of mixing actors with futures, and also lists races between concurrently sent messages and between messages and life cycle actions (creation, lookup, restart, termination).
  - quote: In fact, 29.6% of our Race bugs close over sender(), in the call back of a future or a scheduled message or a task. The anti-pattern behind these bugs is syntactic and can be found using a simple static analysis.
- **C28** [central] Misuse of messaging patterns (request-response/ask, forward, route) is the root cause of 9.7% of the bugs. The worked example is a parent that sends an ask to its child and blocks on the reply: the child throws instead of replying, so the blocked parent cannot restart it, or times out and fails itself. Request-reply with blocking interacts badly with supervision.
  - quote: The root cause of this bug is that the developer misunderstands the semantics of the request-response pattern and its combinations with the semantics of parental supervision and exception handling.
- **C29** [supporting] Explicit, manual life cycle management (creation, initialization, lookup, monitoring, termination, restart) is the root cause of 12.4% of the Akka bugs, for example a parent asking an already-stopped child to clean up in its own postStop. The authors state that frameworks with implicit life cycle management, such as Orleans, are less exposed to this class of bug, which is a point where framework designs differ.
  - quote: Orleans [Bernstein et al. 2014] supports more implicit and automatic actor life cycle management and is less susceptible to bugs that are due to explicit and manual mismanagements of life cycles.
- **C30** [supporting] Model Confusion, which is carrying thread-style assumptions into actor code, is the root cause of 7.6% of the bugs. A key example is failure handling: an actor's exception goes to its parent (supervisor), not to the code that created or messaged it, so a try/catch around actor creation or a send has no effect. The symptoms Incorrect Messaging (for example replies landing in dead letters) and Incorrect Exceptions together cover 27.5% of the bugs and were not in earlier actor bug taxonomies.
  - quote: in Akka, an exception that an actor throws—during its creation or message processing—is caught and handled by its parent actor.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C31** [central] Two actors that each make a synchronous request-reply call to the other (a call cycle) deadlock: each waits on its mailbox for a reply the other cannot send. With Erlang's gen_server:call/2 the default 5-second timeout turns this into a cascading timeout failure instead of a permanent hang. The essay lists the mitigation as 'prefer async casts, use timeouts', enforced only by convention at design time. The Happi Hacking rebuttal (29 March 2026) concedes the deadlock and gives the design fix: 'strict archetypes prevent this by directing calls one way, down the supervision tree'. Status: well established (OTP guidance); bears on sections D (avoid cycles) and H (cyclic dependencies, ask chains).
  - quote: But if a request arrives at Server A that triggers a call to Server B while Server B is already handling a request that calls Server A, then both block forever. Each is waiting on its own mailbox for a reply that will never arrive, because the other server is waiting too. This is a mutex deadlock expressed through message passing.
- **C32** [central] Deadlock-freedom of actor protocols does not compose: per Fowler and Hu (OOPSLA 2026, 'Speak Now: Safe Actor Programming with Multiparty Session Types'), two protocols that are each deadlock-free can deadlock when one actor takes part in both. The stated remedies are one session per actor at a time, or a flow-sensitive (session) type system. Design consequence (inference): a review must check the combined call graph across all protocols an actor takes part in, not each protocol alone. The essay also says static analysis found previously unknown deadlocks in OTP libraries (Christakis and Sagonas, TFP 2011). Status: a research result reported second-hand by a blog; check against the paper.
  - quote: a 2026 OOPSLA paper by Fowler and Hu proves a stronger result: two protocols that are individually deadlock-free can still combine to deadlock in an actor system. The only solutions are restricting each actor to a single session at a time (too limiting for real servers) or building a flow-sensitive type system to thread protocol state through every function call.
- **C33** [central] If mailboxes are unbounded and give no automatic backpressure (as in Erlang), then overload protection must be designed in: an actor that receives faster than it handles grows its mailbox until the node runs out of memory. The essay's mitigation list: monitor sizes, external buffers (Hebert's pobox), back-pressure. The rebuttal adds concrete design rules: a circuit breaker in front of every external dependency, a concurrency limit on every worker pool that calls external services, and backpressure contracts at every domain boundary, with gatekeepers that reply fast errors such as {error, rate_limited} instead of queuing. Status: well established in Erlang practice.
  - quote: Erlang mailboxes are unbounded and provide no automatic backpressure, so if a process receives messages faster than it can handle them, the mailbox grows until the node runs out of memory and crashes.
- **C34** [central] If an actor handles one message at a time and all reads of its state go through it, then an actor that owns widely read data (routing table, configuration store, session registry, lookup cache) becomes a serialization bottleneck: readers queue and throughput collapses. This is the essay's reason why Erlang added ETS, persistent_term and atomics/counters as read paths outside the process. The rebuttal disagrees on the cause: 'mailbox bottlenecks usually signal role confusion, not an inherent flaw in message passing. A Resource Owner that only holds state and answers questions can handle messages in microseconds', so the fix is to split state ownership from I/O, formatting and logging before reaching for shared storage. Status: the bottleneck is well established; its cause and remedy are disputed between the two authors (opinion).
  - quote: This is fine under moderate load, but it becomes a problem when a thousand other processes all need to read from the same data: a routing table, a configuration store, a session registry, a shared lookup cache. The pure model says “send a message, wait for a reply.” Each reader waits in line, the mailbox becomes a funnel, and throughput collapses.
- **C35** [central] State shared through a side channel outside the owning actor reintroduces check-then-act (TOCTOU) races. Christakis and Sagonas (PADL 2010) ran a static race detector, integrated into Dialyzer, on OTP's own libraries and found previously unknown races, clustered in three places: public ETS tables (read-then-write by different processes; multi-key operations not atomic; traversals without snapshot consistency), the global process name registry (register and lookup-then-send races), and the process dictionary. Status: an empirical finding from a scholarly paper, reported second-hand here; supports the anti-pattern 'state shared through a side channel' and the rule that a registry or name lookup followed by a send is not atomic.
  - quote: ETS table races. Process A reads a key from a public table, decides to update it, but Process B modifies it between the read and the write. Classic check-then-act, also known as TOCTOU (“time of check to time of use”).

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C36** [central] Vernon's rule: an aggregate is a transactional consistency boundary drawn around true business invariants, and one transaction should modify only one aggregate instance. Needing to modify several instances in one transaction is a sign the boundaries are wrong or an invariant was missed. (One author's rule of thumb, widely adopted in DDD; he lists four reasons to break it: UI convenience, no messaging mechanism, global transactions, query performance. Mapping aggregate to actor is inference, not in the source.)
  - quote: A properly designed aggregate is one that can be modified in any way required by the business with its invariants completely consistent within a single transaction. And a properly designed bounded context modifies only one aggregate instance per transaction in all cases. [...] If you are modifying multiple instances in a single transaction, it may be a strong indication that your consistency boundaries are wrong.
- **C37** [central] Granularity: design small aggregates. A large-cluster aggregate built on 'false invariants' and compositional convenience causes transaction failures between unrelated user actions and poor performance and scalability; the opposite extreme (stripped-bare aggregates) fails to protect true invariants. The right size is the root entity plus only the attributes that must stay consistent with each other. Vernon cites one project where about 70% of aggregates were a single root entity with value-typed properties.
  - quote: It was deficient from the start because the false invariants and a desire for compositional convenience drove the design, to the detriment of transactional success, performance, and scalability. [...] Rather, limit the aggregate to just the root entity and a minimal number of attributes and/or value-typed properties. The correct minimum is the ones necessary, and no more.
- **C38** [central] Aggregates should refer to other aggregates by identity only, not by direct object reference. This keeps them small, removes the temptation to modify another aggregate in the same transaction, and lets their state be repartitioned and distributed (Vernon ties this to Helland's entities). The stated cost: assembling views needs several lookups, for which he suggests CQRS.
  - quote: Prefer references to external aggregates only by their globally unique identity, not by holding a direct object reference (or “pointer”). [...] Since aggregates don't use direct references to other aggregates, but reference by identity, their persistent state can be moved around to reach large scale.
- **C39** [central] Rules that span aggregates should be met by eventual consistency: the aggregate's command publishes a domain event, each asynchronous subscriber updates one other aggregate in its own transaction, delivery is retried until it succeeds or a retry limit is reached, and on complete failure the design must compensate or report the failure for intervention.
  - quote: Thus, if executing a command on one aggregate instance requires that additional business rules execute on one or more other aggregates, use eventual consistency. [...] This retry process can continue until consistency is achieved, or until a retry limit is reached. If complete failure occurs it may be necessary to compensate, or at a minimum to report the failure for pending intervention.
- **C40** [central] Tie-breaker for transactional versus eventual consistency (attributed to Eric Evans): ask whose job it is to make the data consistent. If it is the job of the user running the use case, keep it inside one boundary; if it is another user's or the system's job, make it eventually consistent. Vernon says this exposes the real invariants better than a technical preference does, and domain experts often accept delays of seconds to days.
  - quote: When examining the use case (or story), ask whether it's the job of the user executing the use case to make the data consistent. If it is, try to make it transactionally consistent, but only by adhering to the other rules of aggregate. If it is another user's job, or the job of the system, allow it to be eventually consistent.

## Source:   (fields: ['claim', 'quote', 'importance'])

- **C46** [central] Actor programs remain prone to a specific, nameable class of protocol errors even with isolation and supervision: waiting for a message that never arrives, sending a message the receiver cannot handle, and sending a wrong payload. The paper attributes this to actor communication patterns being specified only informally, which is its argument for writing the protocol down first (a global type per conversation, projected to a local type per role) and checking each actor against it. Status: well established as a problem statement in the session-type literature; the proposed fix is one research language's approach (Maty), not mainstream framework practice.
  - quote: Nevertheless, actor languages are not a silver bullet: it is still possible—easy, even—to introduce subtle communication errors that are difficult to detect, debug, and fix. Examples include waiting for a message that will never arrive, sending a message that cannot be handled, or sending an incorrect payload.
- **C47** [central] Protocols that are each deadlock-free do not compose into a deadlock-free system: an actor taking part in two conversations can deadlock across them (each send blocked behind a receive in the other session). Maty rules this out by design rather than by extra typing: an actor never blocks inside a handler waiting for a particular message; whenever it needs to receive, it yields to its event loop and installs a handler, so any conversation with a waiting message can run. Design consequence: a blocking, selective wait for one reply inside a handler is the source of cross-conversation deadlock; reactive handlers per protocol state avoid it. Status: proved for Maty (Theorem 4.5); as general design advice it is inference from the paper.
  - quote: In general, just because two protocols are individually deadlock-free does not mean that the system as a whole is deadlock-free, due to the possibility of inter-session deadlocks. [...] Maty does not suffer from inter-process deadlocks because of our event-driven programming style where although an actor is involved in many sessions at a time, only one is running at once, and code within handlers does not block. Since an actor yields and installs a handler whenever it needs to receive a message, the actor can then schedule any handler that has a waiting message.
- **C48** [central] What static multiparty session typing of actors proves, and under which conditions: (1) an actor never sends or receives an unexpected message, (2) no actor is stuck waiting for a message that is never sent, and (3) every ongoing session can eventually communicate, but only if all event handlers terminate. Stated limits: in the Scala implementation single use of protocol state objects is checked at run time, not compile time (violations are turned into failures), and the authors make no formal claim for the session-switching feature ('ibecome'). The guarantee is per session and is not fair termination of every role.
  - quote: type preservation (Theorem 4.2) guarantees that an actor will never send or receive an unexpected message; progress (Theorem 4.5) guarantees that processes never get stuck due to waiting for a message that is never sent because of an unsafe protocol design or faulty implementation; and global progress (Corollary 4.13) guarantees that, in a system where all event handlers terminate, communication is always eventually possible in any ongoing session. - **C111** [central] In OTP, a supervisor has one job: it starts, stops and monitors its children and keeps them alive by restarting them. So in a design, each supervised process has exactly one owner that is responsible for its lifecycle (well established; primary source).
  - quote: A supervisor is responsible for starting, stopping, and monitoring its child processes. The basic idea of a supervisor is that it is to keep its child processes alive by restarting them when necessary.
- **C112** [central] The restart strategy decides how far one child's failure spreads to its siblings: one_for_one restarts only the failed child, one_for_all restarts all children, and rest_for_one restarts the failed child plus every child started after it. So the start order of children is a design decision that encodes dependencies. (The page states the mechanics; that the strategy should mirror dependencies between children is inference, the page gives no explicit 'when to use' rule.)
  - quote: If a child process terminates, the child processes after the terminated process in start order are terminated. Subsequently, the terminated child process and the remaining child processes are restarted.
- **C113** [central] Restarts are bounded, and failure escalates up the tree: when a supervisor sees more than MaxR restarts in MaxT seconds (default 1 in 5 seconds) it stops all its children and itself, and the next supervisor up must then restart it or give up too. A restart is therefore not an endless retry; a repeating fault becomes the parent's problem.
  - quote: If more than MaxR number of restarts occur in the last MaxT seconds, the supervisor terminates all the child processes and then itself. The termination reason for the supervisor itself in that case will be shutdown. When the supervisor terminates, then the next higher-level supervisor takes some action. It either restarts the terminated supervisor or terminates itself.
- **C114** [supporting] Whether a child is restarted is chosen per child, with three types: permanent (always restarted, the default), temporary (never restarted, even when a sibling's failure terminates it) and transient (restarted only after an abnormal exit, not after a normal exit or shutdown). The designer must decide for each process what its ending means.
  - quote: A permanent child process is always restarted. A temporary child process is never restarted (not even when the supervisor restart strategy is rest_for_one or one_for_all and a sibling death causes the temporary process to be terminated). A transient child process is restarted only if it terminates abnormally, that is, with an exit reason other than normal, shutdown, or {shutdown,Term}.
- **C115** [supporting] Knowledge flows one way in the hierarchy: a child should not know its supervisor or even that it is supervised; only the supervisor knows which children matter and when the group ends. The page recommends automatic shutdown (the supervisor of a 'work unit of cooperating children' stops itself when its significant children finish) over a child stopping its own supervisor, which it says makes the tree hard to restructure and can deadlock.
  - quote: A child process does not need to know anything about its supervisor and its respective parent, not even that it is part of a supervision tree in the first place. It is instead only the supervisor which hosts the child who must know which of its children are significant ones, and when to shut itself down.
