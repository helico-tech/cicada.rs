# Design

Described on 2026-11-12 (change loop, Describe), while `turn-observer` is built. The owner handed the decisions of
this change to the main session on 2026-11-11 ("Dor change 5 until 9 i fully trust you"). Every decision below is
made by the main session; each gives the options and why. Reviewed twice; what changed after the first review is marked
"review", after the second "second review".

## Context

What the code does today (release 0.10.0):

- `POST /actors/{type}/{key}/messages` calls `ActorSystem::send_message`. It checks, in this order: the limits of a
  send; whether the id was accepted before (then the answer is "duplicate", whatever else changed); that the type
  is registered (`404`); that the contract has the message type (`422 unknown-message-type`); and, only on a node
  that hosts the type, that the payload decodes with serde (`422 invalid-payload`). A node that does not host the
  type accepts any payload, and the message ends `failed` in its turn.
- `PUT /actors/{type}/{key}` calls `ActorSystem::create_actor`. Every node refuses a state that is `null`; a node
  that hosts the type also decodes the state with serde. Both answers are `422 invalid-state`. A node that does not
  host the type stores any other state, and then every message to that actor fails.
- A contract holds one JSON Schema for the state and one per message type, generated by schemars 1.2 as draft
  2020-12 documents with local `$defs`. Every node can read every contract. `schema.rs` says: "nothing validates
  against them".
- A schema and serde come from the same Rust type, but they can disagree: a field with `#[serde(alias)]`, a
  hand-written `Deserialize`, a number that is too large for its type, a field with `#[serde(with)]` and no
  `#[schemars(with)]`. In the last case the schema refuses what the type itself writes.
- A schema is part of the contract and of its hash. A node whose contract differs from the registered one does not
  start, so a contract cannot change while an actor of the type exists, short of the steps in the operations guide
  under "Changing a contract".
- Only a node registers a contract, at its start. A client over HTTP cannot.
- `cicada-test` checks that state samples still decode (`assert_state_decodes`). Nothing checks a sample against a
  schema.
- No other route takes a payload or a state. A retry sends a stored payload again.
- A send that repeats an id is answered as a repeat when its message is pending or its outcome is still shown.
  An outcome that retention hides is not found by that lookup; the store still refuses the id, after the checks.
- Code can send JSON too: `turn.send_raw` and `ActorSystem::send_message` take a payload as JSON, and nothing but a
  hosting node's decoder checks it.
- The other refusals of what a client sent answer `422`: `unknown-message-type`, `invalid-address`,
  `not-a-watcher`. `400` is for a request that cannot be read: no body, no `state`, a bad policy.
- The end-to-end suite pins today's behaviour: a hosting node answers `422`, and a node that only sends accepts a
  bad payload (`e2e/tests/suite/cluster_api.rs`).

ADR 0018: "A send over HTTP is checked against the registered JSON Schema of its message type, on every node,
whether or not the node hosts the type. A payload that does not match is refused with `400`. serde stays the judge
at the turn. The schemas stay discoverable through `GET /types/{name}`. The test harness checks that a type's
samples pass both."

## Goals / Non-Goals

**Goals**

- A payload or a state that does not match its registered schema is refused over HTTP, by every node, with the same
  answer.
- A host can test that what its clients send passes both the schema and serde.

**Non-Goals**

- Checking sends and creates from code, or with the schema at the turn. That includes JSON that code sends with
  `turn.send_raw` or `ActorSystem::send_message`: it stays unchecked, as today (review).
- A check of a payload that is sent again by a retry.
- Changing how schemas are generated or hashed.
- Making the schema as strict as serde. The door may let through what a turn then fails; it must not refuse what the
  type's own schema allows.

## Decisions

### 1. The validator is in `cicada-axum`; the core calls it where it checks a send

The core gets no validator. It gets two calls that take one more check from the caller:

```rust
/// Checks a payload or a state against its registered schema: `check(schema, value)`, an error with the reason.
pub type SchemaCheck<'a> = &'a (dyn Fn(&Value, &Value) -> Result<(), String> + Send + Sync);

pub async fn send_message_checked(&self, to: &ActorAddress, message_type: &str, payload: Value,
    options: SendOptions, check: SchemaCheck<'_>) -> Result<SendResult, OpError>;
pub async fn create_actor_checked(&self, address: &ActorAddress, state: Value, check: SchemaCheck<'_>)
    -> Result<CreateActorResult, OpError>;
```

`send_message` and `create_actor` are these with a check that accepts everything. The handlers of `cicada-axum` call
the checked ones with the validator. The core runs the check at the place where a hosting node decodes: for a send
after the repeated id, the registered type and the message type; for a create after the registered type and the
`null` check. A refusal is `SendResult::InvalidPayload` or `CreateActorResult::InvalidState`, as for the decoder.
In a create the check also comes before what only a hosting node checks, the address and then the decoder, so that a
state that does not match gets the same answer on every node (validation: decided by the main session on the
validator's report, 2026-11-12).

- **A check handed to the core (chosen, review).** The core keeps the one order of its checks, and the door reads
  nothing twice. The validator itself stays private to `cicada-axum` (second review); the crate's public part is
  the sample checks of decision 9.
- The door checks before it calls the core (this design before the review). It would look up the id and the
  contract itself, two more reads for every send of the typed client, and repeat the core's order by hand.
- The validator in the core. The core would depend on it.

### 2. A repeated send is answered first, as today

The check runs after the core looked the id up, so a send that repeats a message that is pending or whose outcome
is still shown gets the answer of a repeat, also when its payload does not match: a message that code sent as
JSON, repeated over HTTP. A repeat of a message whose outcome retention hides is checked before the store refuses
the id (review); that is how the decoder of a hosting node already behaves.

### 3. The validator is `boon`

| | `boon` 0.6 | `jsonschema` 0.61 |
| --- | --- | --- |
| Draft 2020-12 | yes | yes |
| Crates new to the workspace | 6 | 23 |
| Licence | MIT or Apache-2.0 | MIT |
| Loads a reference from outside | a `file:` address, unless told not to | over HTTP or from a file, with a feature |

Both do what is needed. `boon` adds a quarter of the crates. It has one maintainer and few releases; the check is
one function of `cicada-axum`, so another validator is a change in one place.

The check never loads anything from outside the schema document: no file and no network. `boon` reads a `file:`
reference by default, so the check gives it a loader that refuses every address (second review); the standard
metaschemas are built in. A schema that refers outside itself is a schema the validator cannot use (decision 6).

### 4. Formats are not asserted

Draft 2020-12 treats `format` as a note unless a validator is told otherwise, and the door keeps it so. A validator
and serde do not agree on every date or address. Asserting formats would refuse payloads that the turn accepts.
A payload with a bad date passes the door and fails in its turn, as on a node that does not host the type today.

### 5. The state of a create is checked the same way

ADR 0018 names sends only. The state of `PUT /actors/{type}/{key}` has the same problem and a worse result: a node
that does not host the type stores a state that no node can decode, and every message to that actor fails. The door
checks the state against the state schema of the contract, on every node.

A create is checked whether or not the actor exists, as today: a hosting node already refuses a bad state before it
asks the store.

Not chosen: sends only. The validator and the contract are at hand, and the proposal's reason holds for creates
word for word.

### 6. A schema that the validator cannot use is not enforced

A schema that does not compile (a `$ref` outside the document, a pattern the validator's regular expressions do not
know) is skipped: the door lets the payload or the state through. It logs a warning that names the type and the
message type, once for each such schema in the life of the process, not for every request (review). The door
knows a schema by its text; the check gets no contract hash (second review). The sample check of
decision 9 fails for such a type, so a host finds out in its tests.

- **Not enforced, with a warning (chosen).** A limit of the validator must not make a type unreachable over HTTP on
  every node.
- Refuse every send to that type with `500`. It fails closed, and turns a quirk of a dependency into an outage.

### 7. A hosting node still decodes with serde, and both refusals stay `422`

After the schema check a node that hosts the type decodes the payload with serde, as today. A node that knows a
message will fail should say so. What remains different between nodes is only a payload that the schema allows and
serde refuses, and that is a fault of the type that the sample check finds.

Both refusals answer `422` with the problem type `invalid-payload`, and for a state `invalid-state`, as the decoder
does today. The detail says which check refused it: "does not match the schema" with the place in the payload and
the reason, or "cannot be decoded" with serde's reason.

**This departs from ADR 0018, which says `400` (review).** ADR 0026 records it.

- **`422` (chosen).** No client breaks. In this API `422` is what a client sent that the system cannot take
  (`unknown-message-type`, `invalid-address`, `not-a-watcher`, and these two until now), and `400` is a request
  that cannot be read. A payload that does not match its schema is of the first kind.
- `400` for both, as ADR 0018 says. Every client that matches on the status of a bad payload or state breaks, and
  the two problem types leave the group they belong to.
- `400` for the schema and `422` for the decoder. Two statuses for one problem type.

Not chosen for the decoder: schema only, on every node. Every node would answer the same in every case, but a
hosting node would accept a payload it cannot decode.

### 8. What the detail says

The detail of a schema refusal names the message type (or "state"), then up to five places that do not match, each
with its path in the payload and the reason, and says when there are more. A validator reports a tree: a field of
an optional struct fails under an `anyOf`. The places are the leaves of that tree, in the validator's order
(review), except that under an `anyOf` or a `oneOf` the alternatives that the value cannot be come last: those whose
tag names another variant (a `const` or `enum` on a property of the part fails), whose kind does not fit the part, or
that do not allow a property it holds. So the reasons of the variant that an enum with data names come first, before
"and N more" (validation). To tell, the door looks only at the alternative's own error and its direct causes, at the
part and its properties, never deeper, so that the walk stays linear in the number of errors: a deep value with many
mismatches costs no more than its validation (second validation; an earlier walk over every subtree took seconds).
Two cases the order does not help, as the variant's own error marks it as another: the named variant has a wrong value
in a field that is a unit enum (an `enum` fails on a property of the part), and the named variant of an enum that
denies unknown fields has an unknown field (the part holds a property it does not allow). Its reasons then keep the
validator's order. The detail holds no address of the schema and no path into it; "expected a string" is fine.
A reason may quote the value, so the detail is cut at 2,000 characters and then ends with the mark " … (cut)"
(validation). So is the detail of the decoder of a hosting node, which may quote the value too (second validation).

### 9. The sample checks are in `cicada-axum`

Two public functions next to the check:

```rust
/// Panics unless `sample` (`{"type": "Add", ...}`) passes the schema of its message type and decodes as `M`.
pub fn assert_message_sample<M: JsonSchema + DeserializeOwned>(sample: &Value);
/// Panics unless `sample` passes the state schema of `S` and decodes as `S`.
pub fn assert_state_sample<S: JsonSchema + DeserializeOwned>(sample: &Value);
```

Each says which of the two refused the sample and why, and fails when the schema cannot be used. A host feeds them
what its clients send, and what its own types serialise to. The repository does so for its own types: the examples,
the actors of `cicada-extras`, and `Failed` and `Stopped` (review).

- **In `cicada-axum` (chosen).** The door and its test use one function, and the validator stays a dependency of
  one crate, as the proposal says.
- In `cicada-test`, with the validator as a second dependency there. Two places would have to set the validator up
  the same way.
- `cicada-test` depends on `cicada-axum`. A host without HTTP would build axum for its tests.

### 10. No cache

The door compiles the schema for each request. A schema of a message is small, and throughput is not a goal. A
cache by contract hash can come when someone measures a need. The only thing the door remembers is which unusable
schemas it has warned about (decision 6).

## Risks / Trade-offs

- A payload that serde accepts and the schema refuses was accepted until now and is refused from this release on,
  by every node: a field sent under a `#[serde(alias)]`, a type with a hand-written `Deserialize`. The changelog,
  the README and the operations guide say so, and name the sample check as the way to find it.
- A type whose schema refuses what the type itself writes (a field with `#[serde(with)]` and no
  `#[schemars(with)]`) gets `422` for every send of the typed client, and there is no switch (second review). The
  way out is a right schema, and that is a contract change: a new type name, or the steps of "Changing a contract".
  A host runs the sample checks before it upgrades its nodes.
- Not chosen: a switch that turns the check off for a router. It would be an option that every host has to know
  about, for a fault the sample check finds before a deploy.
- A node that does not host a type lets through what only serde refuses. The message then fails in its turn, as
  today.
- JSON that code sends is not checked (Non-Goals). A turn that creates an actor by address with a JSON state, which
  `cicada-actors` may add, can store a state that no node can decode; the proposal of `cicada-actors` has a line.
- A schema the validator cannot use is not enforced (decision 6). The warning and the sample check are the only
  signs.
- A schema is compiled for each request (decision 10).
- `boon` has one maintainer (decision 3).
- The answer departs from ADR 0018 in its status (decision 7).

## Migration Plan

Version 0.12.0. No migration of the store; nodes of 0.11.0 and 0.12.0 can share a database. During a rolling deploy
a node of 0.11.0 still answers as before.

1. Before the nodes are upgraded: add `assert_message_sample` and `assert_state_sample` to the tests of each type,
   with what the type itself serialises and with what clients send over HTTP.
2. A sample that fails only the schema shows a type whose schema and serde disagree. When it is a form that only
   some clients send (an alias), stop sending it. When it is what the type itself writes, the schema is wrong:
   making it right changes the contract of the type, so follow "Changing a contract" in the operations guide.
3. A client that sent such a form to a node that hosts the type, or anything at all to a node that does not, now
   gets `422` where it got `202`.
